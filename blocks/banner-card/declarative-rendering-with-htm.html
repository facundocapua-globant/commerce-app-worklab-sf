The banner-card rewrite

Same block, same config, same markup and CSS classes — two ways to build it. banner-card.imperative.js follows Adobe's standard pattern for EDS block development (createElement, no build step, codified in this project's own AGENTS.md). banner-card.js is the proposal on the table: the same block, rendered declaratively via htm + Preact. Isolating the block lets the comparison land entirely on the rendering change itself.

01 · The two files

One block, two decorators

Both read the same four config values with readBlockConfig and produce the exact same DOM: a .banner-card-component wrapper, an image, a title, a description, and a “Learn More” link. banner-card.css is untouched by either. The only variable is how the markup gets built.

const BannerCard = ({
  image, title, description, link,
}) => html`<div class="banner-card-component">
    <div class="banner-card-image">
      <img src=${'$'}{image} alt=${'$'}{title} />
    </div>
    <div>
      <h1 class="banner-card-title">${'$'}{title}</h1>
      <p class="banner-card-description">${'$'}{description}</p>

export default async function decorate(block) {
  const { image, title, description, link } = readBlockConfig(block);
  render(html`<${'$'}{BannerCard}
    image=${'$'}{image} title=${'$'}{title}
    description=${'$'}{description} link=${'$'}{link} />`, block);
}
banner-card.imperative.js
banner-card.imperative.jscreateElement, no build step
export default async function decorate(block) {
  const { image, title, description, link } = readBlockConfig(block);

  const card = document.createElement('div');
  card.className = 'banner-card-component';

  const imageWrapper = document.createElement('div');
  imageWrapper.className = 'banner-card-image';
  const img = document.createElement('img');
  img.src = image;
  img.alt = title;
  imageWrapper.append(img);

  const content = document.createElement('div');

  const heading = document.createElement('h1');
  heading.className = 'banner-card-title';
  heading.textContent = title;

  const paragraph = document.createElement('p');
  paragraph.className = 'banner-card-description';
  paragraph.textContent = description;

  const cta = document.createElement('a');
  cta.href = link;
  cta.className = 'banner-card-link';
  cta.textContent = 'Learn More';

  content.append(heading, paragraph, cta);
  card.append(imageWrapper, content);

  block.innerHTML = '';
  block.append(card);
}
Which one actually ships

banner-card.js — the htm/Preact proposal — is the decorator currently loaded by the block framework. banner-card.imperative.js reproduces Adobe's standard EDS block pattern for comparison; it isn't wired up anywhere. It was written specifically to give the proposal a fair, apples-to-apples baseline instead of contrasting banner-card against a structurally different block.

This is the easy case

banner-card is a deliberately basic example: four fixed fields, no conditionals, no lists, no nested components. The 38% gap measured here is a floor, not a ceiling — as a component picks up more fields, conditional rendering, or child components, each addition costs the proposal roughly one line and the standard pattern three to four, so the gap widens with the component's complexity, not just its size.

02 · Where the extra lines go

Cost per concern

Every visual piece of the card costs one line declaratively and several imperatively — not because the imperative version is doing anything extra, but because “create,” “configure,” and “attach” are three separate statements instead of one expression.

Image<img src=${'$'}{image} alt=${'$'}{title} />createElement + .src + .alt + .append (4 lines)

AssemblyImplicit — nesting is assembly2 explicit .append(...) calls to wire the tree back together

Nothing here is hard to write once, imperatively. What accumulates is the ratio: one line of intent (“this is an image with this src and alt”) becomes three to four lines of instructions, and every one of those lines is a place a step can be forgotten — skip the .append, and the element is created but silently never shows up.

04 · What the proposal buys over the standard, specifically here

Benefits of the change

  • 38% fewer lines for the same output. 13 vs. 21 for a block this size — and the gap widens as more fields or conditional rows get added, since each one costs 1 declarative line but 3–4 imperative ones.
  • No assembly step to get wrong. Nesting in the template is the tree; the imperative version needs two explicit .append() calls, and forgetting one fails silently — the element exists, it's just not attached anywhere.
  • Props and markup stay next to each other. src=${'$'}{image} alt=${'$'}{title} sits on one line; the imperative version separates “create the img” from “set its src” from “set its alt” from “attach it,” four statements a reader has to mentally re-group.
  • The component is reusable as a unit. BannerCard is a function that can be composed (<${'$'}{BannerCard} />) inside a larger template later; the imperative version is a block of statements with no natural seam to lift out and reuse elsewhere without also extracting its exact append order.

05 · Performance impact

None worth measuring, for this block

Because both versions now solve the identical, fixed-shape problem, this is as close to a controlled comparison as it gets — and it confirms there's no performance case either way here.

decorate() runs once per block instance, with no re-renders to amortize. The proposal pays for a small vnode tree and a single Preact reconciliation over five static elements; the Adobe-standard version pays for five direct createElement calls with no intermediate representation. Both costs are on the order of microseconds for a block this size — not a difference a user or a Lighthouse run will register.

The one asymmetry that would show up in a network panel is unrelated to either rendering style: banner-card.js fetches htm from unpkg.com at runtime, an extra third-party origin the standard pattern doesn't need. That cost is fixed by pinning htm as a normal dependency, not by rejecting the proposal.

06 · Cognitive complexity

For a regular shape, the standard pattern buys nothing back

Reading BannerCard in the proposal, the shape of the code and the shape of the output are the same shape: given these four props, this markup comes out. There's one thing to hold in your head.

Reading banner-card.imperative.js — Adobe's standard EDS pattern — the same information is spread across 21 sequential statements — create, configure, append, repeat — and reconstructing “what does this render” means mentally replaying the sequence rather than reading a shape. That's the tax the imperative standard always carries, but here it's paid for nothing: there's no conditional structure, no dynamic column count, no cell-spanning logic the proposal couldn't express just as well. When the two implementations produce byte-identical output, the extra sequencing is pure overhead, not the price of handling something the template genuinely can't.

That's the honest boundary of this result: it holds for blocks shaped like banner-card — fixed fields, no conditional structure. Elsewhere in this codebase (a comparison table with a data-driven column count and manual cell spanning, for instance) the same trade tips the other way, because there the imperative standard isn't paying for nothing — it's paying for control the proposal doesn't have a clean way to express.
